# Running 404 with your own agent

404 generates 3D as **code**: one JavaScript module per object that returns a Three.js `Group`.
No mesh files, no downloads.

There are two ways to get that module, and they differ only in who writes the geometry:

- **[A. The open model, on your own GPU.](#a-the-open-model-on-your-own-gpu)** The fine-tuned
  model behind the leader of the live
  [404 generation competition](https://github.com/404-Repo/404-active-competition), deployed
  from a one-click template on your own RunPod account.
- **[B. Your agent writes it.](#b-your-agent-writes-the-geometry)** No account, no API key, no
  GPU, nothing to pay for.

Everything around that step — the reference image, the verifier, the choice made by looking —
is identical for both, and it is where the quality comes from. The loop matters more than the
generator.

---

## The reference image

Generating from a picture beats generating from a description by a wide margin, and it is the
cheapest quality win available.

A name is not a description. Asked for "a shop front" a model invents everything and mostly
invents badly. Measured: "a shop front" failed outright, while "a solid one-storey block with a
striped awning slab and a shutter recessed into the wall" gave usable geometry on 14 of 16
attempts.

**Use one style for the whole set.** Ten objects each generated in their own style give you ten
fine objects and one incoherent set. Fix a single style sentence, reuse it for every object, and
generate the set in one pass.

**This repo does not ship an image generator — your agent sources the references itself.** Some
agents can make images natively. If yours cannot, use any external image tool, or photographs:
they work well for vehicles and street furniture, with the background cut out. What makes a
usable reference: one object filling the frame, plain background, a three-quarter view, even
lighting, nothing cropped. [docs/concept-images.md](docs/concept-images.md) has the details.

**If you have no images at all, this still works, and here is what to do.** Searching the web for
object photographs mostly fails: image search matches words, not pictures, so a query for a wok
on a white background returns a street vendor mid-service. Fall back to writing the object out as
**form, not function**, one paragraph per object: shape, parts, proportion and count, never
purpose. "A shop front" fails outright; "a solid one-storey block with a striped awning slab and
a shutter recessed into the wall" gave usable geometry on 14 of 16 attempts. A whole 26-object
set has been generated this way. Expect it to be worse than working from pictures, which is what
the measurement above says, and expect the loop to carry more of the weight.

Scene frames for the blind comparison are a different matter and are easy to find, since
photographs of real places are everywhere. It is only isolated object references that have no
route.

## A. The open model, on your own GPU

Deploy the [RunPod template](https://console.runpod.io/deploy?template=jg2mrz1rqg). It runs the
stock vLLM server with the open-weights model
([Tooony133/Qwen-3.6-27B-AronHorn](https://huggingface.co/Tooony133/Qwen-3.6-27B-AronHorn),
Apache 2.0) on a single RTX PRO 6000 (~$1.99/hr, on your account, with your key). This is the
model behind the winning entry in the live
[404 generation competition](https://github.com/404-Repo/404-active-competition); the current
best solution is always recorded in that repo's `leader.json`, and the template pins the
round-28 winning revision.

What matters when using it, condensed from the template's readme:

- Set `VLLM_API_KEY` at deploy time — the endpoint is publicly reachable through the RunPod
  proxy. Ready when `https://<podId>-8001.proxy.runpod.net/v1/models` answers. First boot
  downloads ~55 GB of weights (10–15 minutes); restarts reuse the cache.
- **Always stream.** The RunPod proxy drops non-streaming responses after ~100 seconds, and a
  generation can take minutes. Every OpenAI-compatible client can stream.
- One request per reference image: the image plus *"Write a Three.js module reproducing this
  object as `export default function generate(THREE)`. Code only."*
- Sample **three or more candidates per image** at temperature 0.6. Variance between samples is
  the point; the verifier and your eye pick the winner, same as path B.
- **Stop the pod when you finish.** It bills by the hour whether or not you are sending it
  anything, and an idle GPU left running overnight costs more than every asset you generated on
  it. Stopping keeps the downloaded weights, so the next session starts in minutes rather than
  re-downloading 55 GB.

**Then wrap.** The model writes to the competition contract: geometry normalised into a unit
cube, centred on the origin. This repo's contract is real-world metres with the base at
`y = 0`, and `harness/verify.mjs` checks that — raw model output fails the ground check every
time, and its sizes mean nothing. You supply the one fact the model cannot know, the object's
real height:

```bash
node harness/wrap.mjs pod_out/fuel_barrel.js 0.88 -o assets/fuel_barrel.js
```

The output is an ordinary module in this repo's contract
([docs/asset-contract.md](docs/asset-contract.md)). Verify it and load it like anything else.

## B. Your agent writes the geometry

**Three independent attempts per reference image.** Independent means different construction
strategies, not three edits of one file:

- one assembled from primitives: Box, Cylinder, Sphere, Cone, Torus
- one built from profiles: `ExtrudeGeometry` or `LatheGeometry` swept along an axis
- one with a different part breakdown, or a different reading of the reference

Each one written to the contract in [docs/asset-contract.md](docs/asset-contract.md).

## Verify

```bash
node harness/verify.mjs <dir>              # runs node --check on each file first
node harness/verify.mjs <dir> --size=560   # bigger views, when the choice is close
```

**The verifier needs network access**, even though your assets must not have any: it loads
Three.js from a CDN. Offline, every asset fails with `did not load`, which reads as a broken pack
and is not.

It renders every candidate from four sides under identical light, measures it, and writes
`_verify/sheet.png`.

The check that earns its place is the fourth view. An object modelled from the one angle its
reference showed is a featureless box from behind, and every screenshot hides it, because every
screenshot is taken from the good side.

It also catches: doesn't parse, doesn't return an `Object3D`, degenerate bounds, an implausible
real-world size, a base that isn't at `y = 0`, and a triangle count that has run away.

## Pick by eye

Look at the sheet and choose. **Not by triangle count.** The sheet has five views: four
axis-aligned ones that are compared against each other, and a three-quarter view that is not
measured and is there because a recess, a reveal or an opening reads as a flat rectangle from
dead ahead and only shows itself at an angle.

If the choice is close, re-render bigger with `--size=560`. At 320 pixels a control knob is six
pixels across and the detail that separates two candidates is often invisible.

**Which of the three arms wins is largely decided by the object's form**, and knowing that in
advance is worth a whole attempt. Curved and profiled things go to the sweep; boxy joinery goes
to primitives or to a different part breakdown. If your object is obviously one of those, do not
spend one of three attempts on the arm you can already predict will lose. Spend it on a second
genuine reading of the shape. A scoring heuristic once picked a broken
planter at 265,265 triangles over a correct one at 3,880. The numbers tell you what is broken.
They cannot tell you what is good.

If all attempts are poor, the reference is the problem rather than the generation.

---

## Why three attempts

Measured on ten objects. One arm got a single attempt. The other got three plus a syntax check, a
four-sided render and a choice between them. Same model, same references, same output contract.

The second arm won on essentially every object, and the difference was entirely the loop.

Two of the errors it caught in one run, neither of which is a syntax error and neither of which
survives being looked at: an inverted rotation sign that flung a car's windscreen off into space,
and a water tank built 20% too tall because the reference photograph foreshortened its base.

## Using what comes out

```js
import { ASSET } from './harness/assetlib.js';
const car = await ASSET('./assets/hero_coupe.js', { height: 1.44 });
scene.add(car);
```

Copy `harness/assetlib.js` rather than writing your own. The comment at the top of it explains
what that costs: it silently destroyed an entire asset pack across four builds before anyone
noticed.

Plain Three.js otherwise, with no dependency on anything else here.

## Before you start

Read [docs/traps.md](docs/traps.md). Bugs specific to this domain that produce wrong output
**silently**: nothing throws, nothing warns, and the code reads correctly. You will not catch
them by testing the way you normally test.

And run this once, so you know the verifier is actually protecting you:

```bash
node harness/selftest/run.mjs
```

It runs the verifier against assets that are deliberately broken in known ways and asserts each
one is caught. A check nobody has seen fail is decoration.
